# LinkUp implementation plan

Current work (16 October 2026): source version 0.2.5 prepares a two-phone test build with the blue Quiet design and ordered nearby packet sends, including signed replies. Per-connection queues prevent competing Bluetooth transfers, remain bounded, and discard canceled/disconnected work. Earlier app-specific Android PIN/password access, durable new-account deletion, notifications, small fixed-roster encrypted groups, simultaneous setup arbitration and foreground voice/video remain included. Background access is a separate explicit device-key opt-in; see `app/NOTIFICATIONS.md`. The published APK remains 0.1.1. [READINESS.md](READINESS.md) records current evidence and release gates; [the two-phone instructions](app/ANDROID-TESTING.md) describe today’s test. Physical radio/device checks, public service deployment, background calls and independent security review remain pending.

## Accepted scope
Publicly usable free-software messenger, initially for the founder's friends. Android first, web available, iPhone next. Retain the approved Figma mobile style. Include private chats, small groups, file sharing, voice notes, voice and video calls, editable names/photos, QR invitations, emojis, custom stickers, offline delivery, and multiple devices. No public contact search. Online presence is opt-in and defaults off.

## Architecture direction
Use Expo/React Native for a shared interface across native mobile and web. Keep the messaging core independent of UI. Direct authenticated connections are preferred; encrypted relays and optional mailboxes provide connectivity and offline delivery. Provide a default community mailbox with configurable alternatives and self-hosting. A mailbox stores only encrypted envelopes, with expiry, quotas, retry and deduplication; acknowledge storage separately from recipient delivery.

Use established and reviewed asynchronous messaging protocols/libraries, with authenticated per-device keys and forward secrecy. Do not mistake WebRTC transport encryption for end-to-end offline messaging encryption. Choose crypto implementations after a native/web compatibility spike, dependency review, and a written threat model. Never invent a replacement cryptographic protocol for the prototype.

Contacts are established via invitations and explicit acceptance. Invitations must authenticate public identity and never contain private keys. Device pairing uses a separate short-lived, authenticated QR process. Recovery-key backup is the provisional recovery choice. Changing profile names does not change identity. Encrypt profile updates and attachments for their permitted recipients. Profile images must be decoded/re-encoded with metadata stripped before sending.

Follow `app/CRYPTO-LIBRARY-REVIEW.md` for version evidence, provider/storage review, failure/rotation/fork tests and explicit migration constraints. `LEGAL-BRIEF.md` is ready for the owner's review and subsequent consultation; it has not been sent externally.

## First milestone boundaries
The initial UI preview uses sample contacts and in-memory messages. No message leaves the device, no secure identity or real invitation is generated, and no encryption claim is made. Profile edits, selected photos, and preferences are in memory until a secure local store is implemented. Do not use the preview for private data. Call buttons disclose that calls are not implemented. No production hosting or app-store release is performed in this milestone.

## Current progress: experimental encrypted delivery
The vault encrypts profile/presence, contacts, chat history, queues and MLS private state under a stable Ed25519 identity. Signed invitations and full identity-code comparison are implemented. Real friends open real encrypted chats; sample conversations appear only in preview mode. Text, emoji and bundled stickers use MLS through a self-hostable signed HTTP mailbox. A shared vault transaction persists ratchet/outbox before publication and inbox/history/receipts before acknowledgement. Tests and the developer demo use two actual encrypted vault controllers, a real relay, recipient downtime, restart/unlock and replies. The signed standalone Android APK now compiles, installs and launches on an Android 16/API 36 emulator. Its native QuickCrypto primitives and actual MLS message/reply/authentication self-test pass under Hermes. Complete UI messaging and physical-phone tests remain pending.

Milestone 3's relay delivery and application-level nearby delivery are implemented. Android Wi-Fi/hotspot/BLE native adapters are integrated in source. Direct internet P2P, a hosted default community mailbox, background/push delivery, physical-phone QA remain outstanding. This first MLS integration uses fixed two-member epoch 1; commits, membership changes and post-compromise epoch recovery are not enabled. Portable backups, device pairing, media delivery and independent security assessment remain outstanding.

## Messaging and offline milestone
`ts-mls` 1.6.4 implements RFC 9420 suite 1; Common binds key packages and transferable envelopes to the accepted contact's Ed25519 identity and checks exact two-member rosters/signing keys. The Node service has signed one-use challenges, opaque durable messages, recipient acknowledgements, one-use public packages, owner-only key availability, quotas, expiry and restart tests. Claimed private packages survive until their welcome window; the public pool replenishes without losing matching private material. Failed requests keep ciphertext and IDs stable; per-peer backpressure does not block other friends or incoming mail. Verified receipts alone set Delivered.

All unconfirmed messages share the initial package deadline. Explicit mutual Reconnect recovers expired or simultaneous setup without replacing identity or removing visible history; retired groups drain stale packets that could otherwise block a new Welcome. The library and integration are unaudited. Native builds, browser storage/network integration, TLS deployment, capacity/performance testing and independent review remain release gates.

## Invitation milestone
Invitations use domain-separated Ed25519 signatures over canonical public metadata with a seven-day expiry. Parsing validates the exact schema, canonical encoding, identity point and route; expired, changed, ambiguous and unsafe-name invitations fail closed. Acceptance re-verifies the original invitation under the serialized write action. The encrypted contact list refuses self-adds, duplicate public keys and more than 100 contacts. Legacy v1 vaults without contacts keep their original identity and open with an empty list. A signed name is self-asserted; identity comparison remains a human step. Invitations do not authorize transports or encrypted message sessions.

## Next transport work: VPN, local Wi-Fi and Bluetooth

VPN compatibility, local phone-to-phone networks and Bluetooth are requested. The shared delivery interface, persisted policy, nearby protocol and Android source adapters are implemented experimentally. The full native wrapper/Gradle build is complete; physical-phone tests and VPN compatibility remain outstanding; the web/iPhone UI uses the mailbox only.

1. Separate connection delivery from the messaging controller while retaining one encrypted outbox, session state and authenticated receipt path. Add local authenticated public-package exchange so a new conversation can start with no internet/mailbox. Persist state before sending on every adapter; deduplicate the same envelope received through multiple adapters.
2. Test the current HTTPS mailbox over an existing system VPN, including reachable private VPN addresses with valid TLS, tunnel reconnects and split-tunnel/local-network policies. Begin with VPN compatibility rather than embedding a VPN service. Android permits one active VPN service per user/profile; embedding one could displace the user's chosen VPN. WireGuard and optional self-hosted Headscale are external network options, not required Common accounts.
3. Implement foreground local-network messaging through a native Expo module: Android local-only hotspot creation, ordinary Wi-Fi joining and bounded socket transport. Offer QR-based Create/Join without public contact search. Retain HTTPS and the existing browser URL policy; do not relax certificate validation or treat an HTTP LAN origin as a secure website. Android-to-Android Wi-Fi Direct is a later adapter.
4. Implement foreground BLE central and peripheral/GATT roles in the native module. Start with bounded text, emoji and bundled-sticker IDs; fragment/reassemble the existing encrypted envelopes with strict size/time limits, interrupted-transfer retry and receipt checks. Check advertising capability, handle role collisions/disconnects and request nearby-device permissions only when enabled. Never send profile names, permanent public identities or plaintext chat in discovery advertisements. Prefer local Wi-Fi for larger media.
5. Provide a Nearby only policy that disables internet/mailbox delivery and discovery while active. An Automatic policy may choose an available authenticated connection and fall back to the selected mailbox. Show the actual connection honestly; do not label mailbox delivery P2P or claim VPN protection from reachability alone.
6. Test Android foreground/background restrictions, hardware capabilities and current local-network permission rules. The iPhone adapter should use Network framework for local sockets and Core Bluetooth for BLE. Current Apple guidance deprecates Multipeer Connectivity; Wi-Fi Aware is a later hardware/OS-dependent option whose Android/iPhone interoperability needs physical-device testing. Web nearby parity is not promised.

Acceptance checks: two physical Android phones in airplane mode with Wi-Fi/Bluetooth explicitly re-enabled; same-Wi-Fi and hotspot first-contact exchange; BLE-only first contact; restart/unlock and interrupted transfers; duplicate delivery across transport changes; untrusted-peer/tamper rejection; Nearby only producing no internet requests; VPN routing and reconnects; permission denial and unsupported devices; then Android/iPhone tests. Nearby delivery requires devices to come within a usable connection's reach. Always-on reception and multi-hop forwarding are separate milestones.

Primary references: [Android VPN](https://developer.android.com/develop/connectivity/vpn), [WireGuard](https://www.wireguard.com/), [Headscale](https://headscale.net/stable/), [Android local-only hotspot](https://developer.android.com/develop/connectivity/wifi/localonlyhotspot), [Wi-Fi Direct](https://developer.android.com/develop/connectivity/wifi/wifi-direct), [Android local-network permission](https://developer.android.com/privacy-and-security/local-network-permission), [BLE](https://developer.android.com/develop/connectivity/bluetooth/ble/ble-overview), [Apple Network framework migration](https://developer.apple.com/documentation/technotes/tn3213-moving-from-multipeer-connectivity-to-network-framework), [Apple Wi-Fi Aware](https://developer.apple.com/documentation/wifiaware/building-peer-to-peer-apps), [Core Bluetooth](https://developer.apple.com/documentation/corebluetooth), [Web Bluetooth](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API).

## Nearby validation status
The current nearby service supports signed pinned-peer RPC, durable encrypted inbox/claims, route-specific one-use package pools, exact retries, shared MLS sessions and receipts, and no mailbox fallback in Nearby only. The developer demo exchanges first-contact text/emoji/stickers across recipient restart with zero HTTP calls. Wi-Fi/BLE SDK36 helper compilation and ten native JVM tests pass; native Expo wrapper signatures were inspected against SDK57 source. The full Gradle/APK build now passes after repairing a corrupted cache index, bounding native compiler parallelism and disambiguating the Bluetooth wrapper’s zero-argument coroutine. The signed APK installs and launches on an emulator with a passing native MLS self-test. Do not equate Android JavaScript export or packet-channel tests with two-phone radio execution.

Current restrictions: foreground ten-minute sessions, accepted friends, private IPv4 Wi-Fi endpoints, two-minute socket idle closure with manual reconnect, BLE generic discovery and bounded128KiB frames. Automatic uses one route per poll (Nearby while attached, mailbox while stopped), with per-peer availability/backpressure handling. It does not yet choose both routes simultaneously per friend. Nearby only guarantees no Common mailbox requests; an existing VPN can carry socket traffic and its underlying internet connection is outside this app policy.
