# Messaging protocol choice

Common's first networking milestone uses an existing implementation of **MLS (RFC 9420)** instead of designing a key exchange or ratchet. It is an experimental development implementation. The selected TypeScript library has not had an independent security audit, and this integration has not had one either. It must not be presented as a production secure messenger.

## Preferred migration candidate

The [13 October library review](CRYPTO-LIBRARY-REVIEW.md) selects OpenMLS **0.9.1** for the next native/browser feasibility test. The official registry archive checksum was verified; 0.9.1 is listed as patched for the [October recursion advisory](https://github.com/openmls/openmls/security/advisories/GHSA-gc79-23g3-8g52), which affects 0.9.0. The published core audit excludes crypto/storage providers and does not audit Common. Android/Wasm adapters, transactional encrypted provider storage, epoch updates, fork handling and independent integration review remain required. The runtime is still `ts-mls` 1.6.4; no replacement or state migration is implemented.

## Selected development library

[`ts-mls` 1.6.4](https://www.npmjs.com/package/ts-mls) is MIT licensed and implements the MLS protocol. The stable package was updated in August 2026. Its [repository](https://github.com/LukaJCB/ts-mls) explicitly states that the implementation is unaudited. A separate 2.0 release candidate exists; Common pins the stable version and uses its installed declarations, because the main branch documentation describes different APIs.

Common uses only `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519` (standard suite 1). A private conversation is an exact two-member MLS group. A recipient publishes a public KeyPackage while online; the sender can then deliver a Welcome and encrypted messages while the recipient is offline. The protocol defined by [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html) supports asynchronous groups starting at two clients, but Common implements a deliberately narrower subset.

The creator starts at epoch 0 and adds the friend with one setup commit, producing epoch 1. Both clients then require **epoch 1** on every loaded state and application message. Common rejects subsequent commits, proposals, membership changes and other message types. It has no epoch rotation, native multi-member MLS group, device addition or automatic post-compromise recovery. LinkUp 0.2.1 implements small application-level groups by encrypting a separate copy through each accepted friend’s pairwise MLS session; see the fixed-roster group boundary in `SECURITY.md`. Per-message sender and receiver ratchets advance within the fixed epoch; this is not the full MLS epoch-update security lifecycle.

The adapter imports the required **stable 1.6.4 subpaths** for package generation, group creation/joining, the setup commit, private application messages and state codecs. It uses `encodeMlsMessage`/`decodeMlsMessage` and `encodeGroupState`/`decodeGroupState`; main-branch 2.x examples use different APIs. Imports of optional all-suite factories are avoided so Metro does not try to bundle uninstalled post-quantum or unrelated ciphersuites.

Suite 1 is assembled from `ts-mls`'s upstream HPKE/KDF/hash adapters, `@hpke/core`'s X25519/HKDF-SHA-256/AES-128-GCM implementation, the platform cryptographic RNG and `@noble/curves`'s Ed25519 signing implementation. Ed25519 private keys use the same raw 32-byte format on browser and native targets. The application selects these existing primitives and adapters; MLS framing, key scheduling, ratchets and HPKE protocol operations remain in their upstream implementations. This assembly and its identity binding still require an independent review.

Each accepted friend's existing Ed25519 identity authenticates its outer published KeyPackage. The package's basic MLS credential must equal `common:<that identity public key>`, and its package and leaf signatures are checked. The sender pins the remote leaf signing key from that authenticated package. The recipient's identity-signed Welcome binds the sender's ephemeral signing key and group ID; the recipient checks them against the resulting group. Loaded state must contain exactly the expected self and peer identities with those pinned signing keys, the matching group ID and consistent local private keys. Incoming private applications must come from the pinned peer leaf, while the mailbox envelope independently binds the accepted contact and recipient. Common does not use the library's permissive default authentication service. A self-signed leaf alone cannot establish a friend relationship.

## Browser and phone runtimes

`cryptoRuntime.web.ts` preserves the browser's own WebCrypto object. It requires a secure context (HTTPS, or localhost in development) and checks SHA-256, Ed25519 key import/export and signing, X25519 key import/export and agreement, HKDF, HMAC and AES-GCM, including rejection of a changed authentication tag. Missing or broken APIs prevent messaging; there is no weaker fallback.

The native entry point loads [`react-native-quick-crypto`](https://github.com/margelo/react-native-quick-crypto) on demand and installs its native WebCrypto implementation. Version 1.1.8 requires `react-native-nitro-modules` >=0.31.2 and `react-native-quick-base64` >=3.0.0. Its [published API coverage](https://github.com/margelo/react-native-quick-crypto/blob/main/.docs/implementation-coverage.md) includes the standard suite's primitives. The same active checks run after installation. The library is MIT licensed; an OpenSSL-backed implementation or passing these checks does not amount to an audit of Common.

These native modules are absent from Expo Go. An Android or iOS **development build** is required, following [Expo's development-build guidance](https://docs.expo.dev/develop/development-builds/introduction/). Native bundle export only checks JavaScript packaging. It does not verify the native module, phone execution or interoperability. Those must be tested on devices before claiming phone messaging works.

The upstream provider named `nobleCryptoProvider` does not eliminate WebCrypto requirements: HPKE/KDF operations still depend on `@hpke/core`. Common's narrow suite 1 adapter likewise requires the initialized platform WebCrypto implementation. Runtime initialization happens before engine operations; missing modules or failed checks stop messaging explicitly. There is no Expo Go workaround, invented replacement protocol or weaker cryptographic fallback.

## Delivery and durable state

The implemented mailbox holds signed public KeyPackages and opaque protocol messages, never a contact's private package or decrypted chat text. Owner-authenticated challenges protect reads, acknowledgements and key availability queries; identity signatures bind published envelopes and packages. The relay enforces request, size, rate, expiry and storage limits. TLS still matters: message encryption does not hide routing identities, group IDs, timing, sizes or delivery metadata, and it does not authenticate the service itself.

The current implemented transport is the encrypted mailbox. Direct peer-to-peer delivery is pending; it requires discovery/signalling and separate platform integration. The same protocol messages could later travel over an authenticated direct channel. Simultaneous first-session creation is currently refused rather than silently replacing either saved session. Supporting future epoch commits would require an ordering/fork policy on either transport.

Send first saves a local queue entry in the encrypted vault without waiting for HTTP. Sync persists the updated protocol state and exact ciphertext outbox together **before publishing**. On receive, it persists the new protocol state, accepted message, deduplication record and encrypted receipt outbox together **before acknowledging**. Retries reuse the same signed ciphertext and envelope ID. Writers are serialized and stale vault versions refused; locking or pausing revokes in-flight signing capabilities. “Stored” means the relay confirmed storage; only an authenticated encrypted peer receipt marks a message “Delivered.” Ratchet state advances and replaces prior persisted snapshots, but JavaScript strings and garbage collection cannot guarantee immediate memory erasure.

KeyPackages are claimed once. The controller retains matching private material until the Welcome is durably accepted or the package expires. Owner-authenticated availability queries replenish a target pool of 10 available public packages after lost claims; at most 110 private package records are retained, so exhaustion can stop replenishment without discarding available private keys. Public packages are uploaded only after private material is durably saved.

Delivery and package lifetimes are at most seven days. Until a valid peer application confirms the new session, all outgoing packets are additionally bounded by the first-use package deadline. Expired initial setup or competing first sessions require both people to explicitly reconnect the chat and then let one person send first. Reconnect preserves history, marks undelivered outgoing messages for resending and clears the local protocol session. Up to 16 retired group IDs per friend are retained for seven days plus 60 seconds, allowing authenticated old packets to be discarded and acknowledged so they cannot hide a fresh Welcome behind a mailbox backlog. This is delivery recovery: it does not rotate an existing MLS epoch or revoke a compromised Common identity. Identity rotation and automatic post-compromise recovery are not implemented.

The development limits are 10 conversations, 500 messages in total, 8 KiB per encoded application payload including its JSON metadata, 8,192 sender-plus-ID deduplication records and 900,000 UTF-8 bytes for the saved messaging record. The whole encrypted vault retains its existing 1 MiB plaintext limit, including profile data, so a large photo can reduce the available chat history. The engine bounds out-of-order key retention to 128 generations, forward ratchet steps to 200 and historical epoch retention to zero; arbitrarily large gaps are not supported.

Integration tests cover two HTTP clients, the actual encrypted vault, offline first delivery, restarts, exact retries, receipt authentication, reordered Welcomes, duplicate IDs from different senders, failed storage writes, lost package claims, backpressure, cancellation and explicit reconnection with old backlogs. These checks and successful web/Android JavaScript exports do not prove native device execution or independently audit the protocol integration. The fixed epoch provides no implemented post-compromise recovery. Protocol ratchet key deletion also does not hide retained chat history encrypted under the still-available vault key, and the vault has no rollback-proof hardware counter.

## Other routes considered

* **Signal/libsignal:** Its maintained Rust core supports asynchronous Signal sessions, with Java and Swift bindings for phones. However, the [official TypeScript package](https://github.com/signalapp/libsignal#npm) is a Node native addon for desktop operating systems, not a browser or Hermes package. A phone bridge and a separate browser solution are necessary. Upstream explicitly does not support external use. Its AGPL-3.0 license is free software, but distribution obligations need to be preserved. The older [JavaScript implementation](https://github.com/signalapp/libsignal-protocol-javascript) is unmaintained and should not be revived for Common.
* **Matrix Rust crypto:** [`matrix-sdk-crypto-wasm`](https://github.com/matrix-org/matrix-sdk-crypto-wasm) exposes a maintained browser `OlmMachine` with no network I/O. Native mobile needs a Rust/UniFFI adapter; Hermes cannot directly run the Wasm bindings. Matrix's vodozemac implementation is Apache-2.0 licensed and had a [public independent audit](https://matrix.org/blog/2022/05/16/independent-public-audit-of-vodozemac-a-native-rust-reference-implementation-of-matrix-end-to-end-encryption/). A full Matrix client and self-hosted homeserver provide mature offline delivery, while changing the transport model to Matrix federation.
* **OpenMLS:** This MIT-licensed Rust implementation is a stronger production candidate with a [2026 independent audit](https://blog.phnx.im/openmls-independent-security-audit/). Its [platform notes](https://github.com/openmls/openmls#supported-platforms) say Android, iOS and Wasm are built but not tested on upstream CI. Its minimal [Wasm bindings](https://github.com/openmls/openmls/tree/main/openmls-wasm) are an experiment, not a complete persisted browser SDK. Common would need a native adapter, browser bindings and storage integration. A [React Native example from Margelo](https://margelo.com/blog/building-e2e-encrypted-group-messaging-with-openmls) demonstrates the Rust/FFI/Nitro route. The audited crate does not automatically audit these new boundaries; pin patched versions and check upstream advisories.
* **Noise:** The [Noise framework](https://noiseprotocol.org/noise.html) supplies established authenticated transport handshakes. It does not by itself supply a complete asynchronous messenger with prekey lifecycle, message ratchets and durable offline state. Its one-way patterns are not a substitute for Signal or MLS's full state management. It may be useful for an additional direct transport later.

For a reviewed release, prefer a maintained native Rust core shared with the browser through Wasm, or a mature full messaging stack, and obtain an independent review of identity binding, storage and delivery. The development TypeScript path makes the two-client workflow testable while keeping its limitations explicit.
