# Development security status

This development build has encrypted local vault storage, signed invitations, experimental pairwise MLS messaging and fixed-roster encrypted group fanout through a self-hostable mailbox. Foreground voice/video calling and Android nearby adapters are implemented; physical-phone interoperability remains unverified. Optional Android background notifications/replies add the explicitly delegated device-key boundary documented below and in `NOTIFICATIONS.md`. Direct internet P2P transport, multi-device pairing, background calls and media-file delivery remain unfinished. The MLS library/integration are unaudited; this must not be marketed as a production secure messenger. See `THREAT-MODEL.md`, `MESSAGING-PROTOCOL.md` and the latest `../READINESS.md` entry.

## Security implementation followup for 0.3.0

The October 16 fixes are included in the signed local 0.3.0 test APK. Packaging verifies the exact current bundled source, native engine, OpenSSL version, VPN service configuration and license assets. This is not a public release or an independent audit. New v2 sessions use standard MLS UpdatePath commits, alternating both members after 64 chat events or 24 hours of active syncing, with durable exact commit retries, epoch-bound encrypted acknowledgments, bounded historical receive epochs, and fail-closed expiry. Existing sessions remain readable but require explicit reconnection on both upgraded phones before new sends. Exactly two prior receive epochs are retained. Packets maliciously delayed across more cycles are rejected rather than retaining old secrets indefinitely. Ordinary offline delivery cannot advance a cycle without the peer’s acknowledgment. This closes the fixed-epoch implementation gap; it does not make `ts-mls` independently audited. OpenMLS remains a migration candidate, not the current backend.

The relay now defaults to denying strangers. A signed, monotonic recipient permission list controls package claims and mail, including durable revocation/tombstoning and legacy snapshot migration. Relay operators can therefore observe an accepted-friend graph; this is an explicit metadata tradeoff. Unauthenticated challenge issuance no longer charges a claimed victim identity's quota. Global abuse and malicious accepted friends still need operational controls. Removing a friend atomically cancels local queued work, retires its live MLS session, preserves read-only history and advances the durable permission revision. Already-stored mail at the other recipient can still arrive; offline revocation is shown as pending. A v1 relay upgrade deliberately drops old pending ciphertext.

Android applies `FLAG_SECURE` before activity content; React Native 0.86.3 propagates it to modal windows. Screenshot/recents behavior still needs device checks. Existing opt-in background key access remains a separate disclosed boundary. Account reset also deletes the independent VPN key wrapper and enrollment.

The new Android private-network prototype uses the official WireGuard backend, separate Keystore-encrypted native tunnel keys, explicit Android consent, expiring per-phone enrollment, exact friend routes, and TLS certificate-pinned sockets bound to the overlay. Identity-signed connection offers and MLS remain mandatory. Stop/revoke/lock invalidate native socket leases. Private-network mode keeps mailbox delivery off; it deliberately refuses calls until overlay-specific media routing is implemented and verified. It does not protect all traffic on the phone, hide metadata from the hub, or provide direct internet P2P. See the [self-hosted setup](../deploy/vpn/README.md).

The final JavaScript regression run passed all 237 app tests; all 35 relay and 3 generated-server-policy tests also passed, with lint/typecheck/web export. Android assembly and 22 native JVM tests passed; three additional permanent dependency-substitution regressions passed. These include the actual 64-message renewal threshold and direct call renewal deadline. A bounded cache stores only digests of successfully verified public signatures; freshness, recipient, owner, shape and permission checks still run on every use.

The WireGuard Android JNI engine was rebuilt with Go 1.27.2 and current pinned modules, replacing the AAR’s unsupported Go 1.24.3 copy. QuickCrypto’s OpenSSL 3.6.2 was replaced by a source-built 3.6.5 Prefab artifact. Published primitive vectors passed against that exact OpenSSL static library on Android; the rebuilt WireGuard library loaded and reported its expected revision. Source checks, hashes, notices and limitations are in `legal/wireguard` and `legal/openssl`. These do not establish security of every native bridge or independent cross-host reproducibility. OpenSSL 3.6 support ends November 1, 2026; move to a supported dependency baseline before then.

No server has been provisioned. A real hub, two-phone cross-network/blocked-UDP/lock/revoke tests, the remaining native dependency assessment and independent application/protocol assessment remain release gates. Passing local tests is not production approval.

## Historical source review of 0.2.5 on October 16, 2026

**Verdict: experimental; not approved for sensitive or production use.** This review inspected the local 0.2.5 source and its identity/invitation, vault/unlock, MLS state, mailbox, nearby, call, notification and update boundaries. It is an internal source review with regression tests, not an independent audit, penetration test, formal proof or physical-device assessment. The existing downloadable 0.2.5 APK predates the fixes below; changing source does not update an installed APK.

The table below records the findings at the time of the 0.2.5 review. The 0.3.0 followup above gives the current implementation status.

| Priority | Finding and consequence | Status |
| --- | --- | --- |
| High | `src/messaging/mlsEngine.ts` permits only epoch 1 and rejects later commits. Stealing current messaging state can expose subsequent traffic until sessions are replaced; there is no automatic post-compromise recovery. | Open. Implement reviewed MLS epoch evolution, durable commit delivery, concurrency/fork handling, old-secret retirement and migration together. |
| High release gate | Installed `ts-mls` 1.6.4 explicitly disclaims a formal security audit in its packaged README. Primitive choice and passing tests do not establish protocol/integration security. | Open. Reassess the candidate in `CRYPTO-LIBRARY-REVIEW.md` against current upstream releases and advisories before migration. Independently review the complete integration. |
| Medium | `src/calls/protocol.ts` accepted mixed SDP line endings. Entries separated by bare LF/CR could escape the CRLF-based media/candidate checks. | Fixed in source: require consistent CRLF before policy parsing. Regression reproduced acceptance before the fix. Native-engine exploitation was not demonstrated. |
| Medium | `src/calls/mediaCore.ts` filtered incoming/trickled local-only candidates but omitted checks on locally generated offers/answers with inline public candidates or public connection addresses. | Fixed in source: validate outbound SDP before setting or sending it; refuse stale completion after a connection changes. Regression reproduced the missing rejection. This is not a verified OS-level VPN kill switch. |
| Medium | `src/updates/release.ts` read entire network responses with `text()` before checking character counts. A compromised endpoint could cause excessive allocation; multibyte bodies also bypassed the intended byte budget. | Fixed in source: stream with 256 KiB listing / 16 KiB manifest byte limits, reject oversized headers, cancel on overflow/abort, decode strict UTF-8, omit credentials and disable metadata caching. Preserve publisher signatures and native APK checks. |
| Medium before public hosting | Relay authentication proves control of a key, not friendship. `relay/store.mjs` allows any other authenticated identity to claim a recipient's one-use packages and submit bounded mail. A loopback HTTP reproduction with disposable identities consumed all ten published packages from an unrelated account; see `artifacts/security-review-relay-admission.json`. Repeated claims/spam can exhaust availability despite quotas. | Open. Recipient-issued, sender-bound authorization, revocation and abuse controls require a coordinated client/relay protocol revision. Do not interpret accepted-contact checks on the client as server-side admission control. |
| Medium privacy gate | No screenshot/recents protection is configured. Opt-in background reply access intentionally allows the device to decrypt without the app PIN while the phone is unlocked. Direct call/BLE routing exposes metadata. | Open/disclosed. Add screen-privacy controls, review delegated key lifetime, and test device lock/Doze/Keystore and actual network routes on phones. |

The reviewed design uses independent random vault/identity keys, authenticated vault encryption, signed recipient-bound invitations/nearby offers, identity-pinned MLS credentials, authenticated call signaling and DTLS-SRTP, and signed release metadata plus APK hash/package/version/signer checks. These are useful controls, not a claim that all information is encrypted: public keys, invitation names, IP addresses, traffic sizes/timing and relay routing records remain observable in their respective channels. There is no post-quantum claim. Saved history is readable after unlocking its vault even if transport message keys are retired.

[RFC 9420 §16.6](https://www.rfc-editor.org/rfc/rfc9420.html#section-16.6) explains why fresh, processed epoch commits are needed for post-compromise security. [RFC 8828](https://www.rfc-editor.org/rfc/rfc8828.html) describes WebRTC address exposure and VPN routing concerns. An added VPN cannot repair endpoint compromise or the missing MLS epoch evolution. See the October 16 private-network design in [PRODUCT-NOTES.md](../PRODUCT-NOTES.md).

Validation is recorded in `artifacts/security-review-2026-10-16.json`: **204/204 app tests**, **33/33 focused call/update checks**, **26/26 relay tests**, lint, typecheck and web export pass. Nine new regression cases cover the fixes. Browser voice/video checks passed with synthetic media, authenticated DTLS in both directions, simultaneous recovery and cleanup; no real microphone/camera was opened. An initial full run had one nearby concurrency test exceed its one-second fixture deadline under CPU contention. It passed in isolation; that serialization test now allows ten seconds, and the final full run passed. Production's sixty-second timeout and explicit rejection-test deadlines are unchanged. No physical-radio, TURN, native APK rebuild, public service or VPN deployment is claimed by this review.

## Dependency review — updated October 16, 2026

The generated Expo SDK 57 dependency tree reported npm advisories. Applied narrowly scoped overrides:
- `xcode` uses `uuid` 11.1.1 to replace the vulnerable 7.x transitive dependency.
- `decode-uri-component` uses 0.5.0 to replace the vulnerable version inherited by routing dependencies.
- `ts-mls`'s pinned older Noble peer ranges are overridden to the project's existing 2.4 releases. Common imports only the tested RFC 9420 suite 1 provider and standard submodules; unused optional suites are not bundled. Interoperability is tested against the upstream default provider.

The current scan reports **20 high entries, zero moderate/critical**, arising from two advisories and their dependent packages, not twenty independent crypto flaws. The relay scan reports zero advisories. `npm explain` traces `braces` through `micromatch`, and `node-forge` through Expo CLI/code-signing tooling. None of `braces`, `micromatch` or `node-forge` appears among the 1,863 sources in the existing Android release bundle map. This narrows the observed runtime exposure; it does not clear the development/build environment or native dependencies. Audit evidence is in `artifacts/audit-app-security.json`. QuickCrypto is reported through the dependency chain; do not force npm's proposed native/Expo downgrades. This remains a release gate. New cryptography packages and native OpenSSL/Nitro integration still require their own review.

`braces` 3.0.3 and `node-forge` 1.4.0 remain affected; both are still the latest registry versions on October 16 and both advisory pages list no patched version. Keep build tools away from untrusted patterns/certificates, reassess upstream fixes, and resolve or independently justify the remaining exposure before production. A passing build or npm audit is not a security audit.

## Privacy requirements confirmed October 13, 2026

The user requires lawful operation, user control and no intentional backdoors. No developer/admin master decryption key, key escrow, hidden recovery account, plaintext relay endpoint, secret key-upload telemetry or encryption downgrade is permitted. Recovery must remain controlled by the user. These are design/review requirements, not proof that dependencies, builds or future updates contain no vulnerabilities. Do not advertise Common as impossible to crack, anonymous, quantum secure, independently audited or production secure.

| Data / boundary | Current behavior | Remaining work |
| --- | --- | --- |
| Text, emoji, bundled sticker IDs and receipts | MLS application encryption before delivery | Independent review of implemented epoch updates and recovery after compromise |
| Profile, photo, contacts, history, outbox, MLS state and appearance | Authenticated local-vault encryption | Hardware cache/backup behavior; rollback protection; user-controlled backups |
| Web vault key | User-held key, memory during explicit unlocked session | Hosting/update security review; compromised scripts can steal it |
| Native vault key | Explicit recovery-key or opt-in authenticated SecureStore unlock. A separate background-messaging opt-in permits a Keystore-encrypted key copy while the phone is unlocked, without app biometric authentication | Verify real Keystore/Keychain access, enrollment changes, cancellation and lock races on physical phones |
| Invitations / nearby QR | Signed public identity/connection information | Invitation names and QR hotspot credentials are visible to anyone who sees the code |
| Relay / BLE routing | Ciphertext content, visible identities, timing and sizes | Metadata reduction and operational abuse resistance; recipient permissions are now enforced |
| Calls and remaining media | Authenticated DTLS-SRTP calls implemented; disabled in private-network mode. Attachments, device sync and backups remain unfinished | Independent call review and end-to-end media formats |

Browsers lock on hidden visibility or pagehide immediately. Native sessions lock after 30 continuous seconds inactive/backgrounded, allowing a bounded return from photo pickers/permission prompts. Private operations/signatures require foreground access during that grace period; network jobs cancel immediately. Returning does not unlock a locked vault. Lock clears private UI snapshots, revokes pending operations and best-effort wipes owned vault-key byte arrays. JS strings, garbage collection and dispatched storage/network actions cannot be recalled or securely erased by this mechanism. App-switcher snapshots, screen capture and native timers under OS suspension remain hardware review items.

Appearance choices get no new plaintext storage writes. Preview choices are memory-only. Old `common.appearance.v1` records migrate after unlock and are removed only after encrypted persistence succeeds; failed migration retains the original and reports failure. Deletion is not forensic erasure; old OS backups may retain prior plaintext.

## Research and next security milestones

The [library review](CRYPTO-LIBRARY-REVIEW.md) selects OpenMLS 0.9.1 as the preferred migration candidate and records archive verification, advisory checks, audit scope and required feasibility tests. This is a candidate decision, not a runtime replacement or approval for production. The [legal brief for Croatian counsel](../LEGAL-BRIEF.md) describes the operating models and questions requiring advice before launch.

[RFC 9420, section 16.6](https://www.rfc-editor.org/rfc/rfc9420.html#section-16.6) requires fresh epoch updates for recovery after compromise; new v2 sessions now process alternating epoch updates; independent review of their integration remains required. [Signal's Double Ratchet specification](https://signal.org/docs/specifications/doubleratchet/) is a reference for key evolution and skipped-key handling, not code to mix into MLS. [OWASP MASVS storage](https://mas.owasp.org/MASVS/controls/MASVS-STORAGE-1/) and [cryptography controls](https://mas.owasp.org/MASVS/controls/MASVS-CRYPTO-1/) guide review; Common is not certified against them. The [ts-mls maintainer](https://github.com/LukaJCB/ts-mls) reports no formal security audit.

Priorities before sensitive conversations:
1. Select and independently review the production protocol/library. Complete authenticated epoch transitions, durable commit delivery, simultaneous updates, obsolete-secret retirement and recovery/revocation tests. Do not bolt a custom ratchet onto the experimental protocol.
2. Authenticate device unlock; review keystore access, enrollment, caches, backups, screen exposure and lock behavior on phones. Saved history remains accessible to a holder of its vault key even when message keys rotate.
3. Reduce metadata and protect key-package access with recipient-issued permissions. Independently review the implemented authenticated WebRTC calls and encrypt future attachments end to end; keep push notifications generic and external services free of message keys/content.
4. Review browser delivery: HTTPS, restrictive response headers/CSP, no third-party runtime scripts, safe rendering/media parsing, invitation/referrer/access-log handling and authenticated, reviewable updates. A server-controlled web update can replace the client; open source alone does not prevent this.
5. Resolve dependency advisories; verify locked build inputs; produce signed, reviewable releases and assess reproducibility. Direct Noble/scure dependencies now have exact pins. Conduct an independent application/protocol assessment and two-phone/network tests.

Post-quantum migration requires a separately reviewed, interoperable protocol. [NIST's published standards](https://csrc.nist.gov/News/2024/postquantum-cryptography-fips-approved) provide primitives; changing an algorithm name does not establish quantum resistance. Common's current suite uses classical X25519/Ed25519 and makes no post-quantum claim.

## Legal review before public operation

Croatia is the confirmed operating jurisdiction; EU law also matters. This records engineering research, not legal clearance. Developing software and operating a public communications/relay/VPN service require separate analysis. Free distribution, non-profit intent and decentralization do not automatically remove obligations.

[Croatia's Electronic Communications Act, Article 52](https://narodne-novine.nn.hr/clanci/sluzbeni/2022_07_76_1116.html) contains interception and encryption-related duties. Paragraph 13 explicitly addresses services supplied with or without payment and refers to Articles 53–54 as well. [HAKOM lists the current Acts](https://www.hakom.hr/hr/zakoni-2038/2038), including the [2026 amendment](https://narodne-novine.nn.hr/clanci/sluzbeni/full/2026_04_45_523.html). A qualified Croatian lawyer must determine applicability to the publisher and each service-operating model. Do not assume that free distribution, P2P architecture or missing telephone numbers makes these provisions inapplicable.

The [European Court of Human Rights' Podchasov judgment](https://hudoc.echr.coe.int/eng?i=001-230854) found the particular blanket decryption obligation disproportionate because it risked weakening encryption for all users. It is not a universal exemption from lawful orders or a definitive ruling on Common's Croatian deployment. The [Council's July 2026 announcement](https://www.consilium.europa.eu/en/press/press-releases/2026/07/23/fighting-child-sexual-abuse-online-interim-measure-protecting-children-now-reinstated/) concerns voluntary detection and excludes the specified encrypted number-independent services; long-term proposals must not be presented as enacted requirements.

Public launch requires operator classification, applicable interception/notification duties, privacy/retention practices, lawful-request handling and distribution/artwork licence review. [HAKOM's DSA guidance](https://www.hakom.hr/en/hakom-reminds-the-deadline-for-submitting-notifications-by-intermediary-service-providers-expires-on-29-october-2025/12273) includes messaging/VPN examples. [GDPR Articles 25 and 32](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32016R0679) address privacy by design and security, including encryption; encryption does not eliminate obligations for personal metadata.

No public/default service has been deployed. Continue private prototype work; obtain qualified advice before choosing a public operating model. If applicable obligations conflict with the no-backdoor requirement, review that model with the user and counsel instead of silently weakening the app or claiming laws can be ignored. Do not contact authorities or publish/deploy on the user's behalf without authorization.

## Nearby transport integration
The nearby protocol reuses the existing signed envelope/package domains and adds signed request-hash-bound peer responses. The new `common/nearby-offer/v1` vault signing context binds ten-minute QR offers to both accepted identities, local endpoint/TLS pin or BLE service, expiry and nonce. Offers can include temporary hotspot credentials; share them with the intended friend. The service persists encrypted inbox packets, key claims and dedup tombstones before confirming storage. Same-identity retries cannot reuse a one-use package across mailbox/nearby routes.

Wi-Fi certificate pinning applies only to the native peer socket. The global browser/mailbox HTTPS policy is not weakened. BLE application packets remain MLS encrypted, but Bluetooth framing does not conceal permanent routing identities or other traffic metadata. Nearby only stops LinkUp mailbox traffic; it is not a claim that the operating system/VPN makes no internet connections. The module requests nearby permissions only for selected actions, starts foreground sessions and stops resources on background/destroy. The 0.2.5 release passed native assembly and emulator upgrade checks. Physical keystore/TLS behavior, hotspot address discovery, Bluetooth interoperability and actual VPN routing remain release gates. Compilation and internal tests are not an independent security audit.

## Historical optional biometric vault unlock (before 0.2.2)

This describes the earlier method, retained for compatibility. Current new-account access uses an app PIN or long password, as described below and in `ACCOUNT-ACCESS.md`.

Supported phones may opt in only from an unlocked vault. `expo-secure-store` uses `requireAuthentication: true` on a fresh, separate Keychain/Keystore alias for both writing and reading the vault key. Enrollment requires authenticated read-back before a non-secret opt-in marker is committed. No JavaScript authentication-success flag releases an unprotected key. The older unauthenticated convenience entry is never read and is deleted on successful manual unlock or enrollment; new setups never write it. Startup reads availability and the marker only, and stays locked until an explicit action. Lock, background loss or a changed controller generation invalidates pending completion.

The vault cipher and recovery key are unchanged. There is no short numeric PIN encryption mode and no service-held recovery secret. The recovery key remains necessary if biometrics change or the protected item is lost. It cannot recover a deleted vault. Web does not persist the key or pretend that browser biometrics are supported. Node adapter/lifecycle checks are not proof of hardware enforcement; both Android and iOS need physical validation. See the [Expo SecureStore contract](https://docs.expo.dev/versions/v57.0.0/sdk/securestore/) for biometric invalidation and platform behavior.

## Optional Android background notifications and encrypted groups (0.2.1)

Background notifications/inline replies introduce an explicit, separate device-key access choice. A Keystore-encrypted vault-key copy can be accessed while the phone is unlocked without an app biometric prompt. This is off by default and described before opt-in; it must not be described as equivalent to biometric-only protection. Phone lock, native delivery-policy revocation and disabling the option gate the background port. UI and background writes share a serializer and reload the same encrypted record. See `NOTIFICATIONS.md` for the complete boundary, lifecycle and validation checklist. Physical Keystore/notification enforcement remains unverified.

UnifiedPush wakes the client through its maintained Apache-2.0 connector and RFC 8291 Web Push. The relay sends a content-free encrypted hint. Actual chat data still passes identity signatures, accepted-contact checks, MLS authentication, replay controls and durable storage. The provider and mailbox still observe routing/timing metadata. Approved HTTPS provider origins, connection-time public-DNS enforcement, bounded queues, endpoint expiry, retries and no redirect following constrain relay abuse; they do not eliminate every denial-of-service risk.

Small groups use independent existing pairwise MLS channels and an owner-signed, immutable roster. This is pairwise fanout, not a multi-member MLS epoch implementation. The `common/group/v1` identity-signature context binds group ID, title, creator, creation time and every member's key/name. A received message must come from a signed roster member. Joining is explicit; each member must already be an accepted friend, and pending/left groups cannot send. Group control packets stay out of private chat history. Recipients can retain or share what they received; leaving cannot revoke previously delivered plaintext. Dynamic member addition/removal, group epoch changes, post-compromise recovery and group calls remain future work. No new production-security or cryptographic-audit claim is made.


## Historical account-access update (0.2.2; archive policy superseded by 0.2.4)

New sign-up now saves an authenticated phone unlock method or a scrypt-wrapped local password before writing the first encrypted vault. Raw recovery-key handling is legacy-only UI. Android 11+ uses an AES-256-GCM Keystore key with per-operation strong biometric/device-credential authorization through the system CryptoObject; this is separate from the explicitly delegated background-notification key. Passwords use the fixed bounded scrypt N=32768/r=8/p=3 profile, independent random salt/nonce, and XChaCha20-Poly1305 wrapping of the existing random vault key. Offline resistance depends on password strength. No server-side password reset/key escrow has been added.

The locked-screen new-account path verifies the old encrypted vault/password archive before removing the active record. It changes public identity and revokes old background access. Android retains the old protected phone key/ciphertext for the archive under a separate account alias, then detaches it from active use; an archive still needs its original unlock method. Account archives remain local, are capped at three and have no export/restore UI in this revision. See [ACCOUNT-ACCESS.md](ACCOUNT-ACCESS.md) for failure ordering, device-lock limitations and validation requirements.

### App-specific Android PIN (0.2.3)

A six-digit PIN now uses a native device-bound Keystore HMAC secret, PBKDF2-HMAC-SHA256 (600,000 iterations) and AES-256-GCM wrapping; it is not a six-digit substitute for the long-password scrypt wrapper. No system screen-lock PIN is used for routine app PIN setup/unlock. Native attempts persist before decryption, with escalating waits using monotonic time and boot count. Limits are software enforced and can be bypassed by root/app compromise; they are not hardware anti-rollback. See ACCOUNT-ACCESS.md for boundaries, migration and archive key retention. Web keeps a long password. Existing optional background reply access remains separately disclosed. Physical device validation and an independent audit are outstanding.

### Permanent new-account deletion and bridge correction (0.2.4)

Creating a new account now deletes prior local data and every earlier local archive. A verified intent marker makes interrupted cleanup resumable. The shared write lock and native background-access revocation prevent stale jobs from restoring deleted state. Native PIN/phone namespaces and keys, legacy protected records, notification keys/replies, app-owned storage and private caches are removed. Fresh signup cleans residue even if an earlier attempt already removed the active vault. UI warns before deletion. It does not delete gallery originals or remote copies and cannot guarantee forensic flash erasure. The old phone-disable bridge now returns Unit rather than a KeyStore object; failures still reject. See ACCOUNT-ACCESS.md for the current policy.

Background transactions also check the durable deletion marker before opening an old vault or creating a signer. A restarted notification job with stale native opt-in cannot bypass an interrupted reset; observing the marker revokes that port. This path has a dedicated regression test.
