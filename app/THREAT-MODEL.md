# Local vault threat model — development foundation

## Scope
The vault protects the saved profile/photo, appearance, opt-in presence preference, contacts, history, outbox and MLS private state under a stable Ed25519 identity. Signed invitations authenticate public identity keys; users compare full identity codes to establish who owns them. Experimental text/emoji/bundled-sticker network messages use MLS through a self-hostable mailbox. Device pairing, media delivery and backup export/restore are not implemented. Sample chats remain in memory and never leave preview mode.

## Construction
- Independent 256-bit random vault key and 256-bit Ed25519 seed from Expo's asynchronous cryptographic random API.
- XChaCha20-Poly1305 authenticated encryption from `@noble/ciphers`, with a fresh random 192-bit nonce for each write.
- A fixed authenticated context string binds records to the Common local-vault format. Envelope version, algorithm, nonce, size, and decrypted schema are checked.
- Ed25519 public key is recalculated from the decrypted seed before accepting identity data; profile edits do not modify the identity.
- Vault contents are encrypted in AsyncStorage. Current Android setup wraps the random vault key using a separate six-digit app PIN plus a non-exportable Keystore HMAC secret, PBKDF2-SHA256 and AES-GCM. Retry limits are persisted software controls, not hardware anti-rollback. Long passwords use scrypt and XChaCha20-Poly1305; web persists this encrypted wrapper, not a plaintext key. Legacy authenticated biometric/phone methods remain readable. See `ACCOUNT-ACCESS.md` for the current access policy.
- Startup stays locked. Browser hiding/pagehide locks immediately; native inactive/background states allow 30 seconds for system pickers before locking. UI private operations require foreground access and its network jobs cancel on background. Separately opted-in Android notification work has its own Keystore-encrypted vault-key copy and can decrypt while the phone is unlocked without the app PIN; it checks opt-in, device-lock and delivery policy. Returning does not auto-unlock the UI. Native timers, Keystore enforcement and app-switcher exposure still need physical checks; Android now applies FLAG_SECURE to activity and inherited modal windows; physical screenshots/recents enforcement still needs verification.
- Appearance lives inside the encrypted vault. Preview choices are ephemeral; old plaintext settings are deleted only after encrypted migration succeeds. Old OS backups and deleted file remnants may retain the former plaintext settings.
- New signup saves an unlock wrapper and does not require handling a raw recovery key. Legacy key unlock remains available. A lost PIN/password has no server reset or escrow. Explicitly starting a new account permanently deletes the old local account and older local archives; it creates a different identity. A key cannot recover a deleted vault; portable backup/restore remains unfinished.
- The UI operation queue and shared native background write serializer coordinate writes. Native edits reopen the newest same-identity record before changing it, preserving background messaging updates. Browser Web Locks plus expected-record comparison prevent simultaneous tab creation and reject stale writes. Browsers without Web Locks fail closed for vault writes.
- Corruption, wrong keys, or storage failure do not trigger automatic creation/reset of identity or overwrite the old record.
- A shared operation controller invalidates pending work on Lock, cancellation, or effect teardown. A storage write already dispatched cannot be recalled; a completed cancelled setup remains locked. Manual recovery unlock removes the legacy unprotected convenience entry and does not create a new unauthenticated cache. Optional biometric and background copies require their own explicit setup.
- Profile photos are decoded, cropped, resized and encoded to JPEG before saving. Native generated cache output and recognized picker cache copies are removed. Gallery originals are untouched. Native cleanup still requires hardware verification.

## Invitation and contact construction
- Seven-day invitations contain version, public Ed25519 key, display name, issuance/expiry timestamps and a random 128-bit nonce. A domain-separated Ed25519 signature covers exact canonical JSON encoded as canonical base64url.
- Inputs are bounded; only raw tokens or exact native/web invite routes with a single token parameter are accepted. Parsing rejects extra/duplicate fields, alternate encodings, control/bidi names, malformed Unicode, expired/future times, and noncanonical/small-order/mixed-torsion public keys.
- Signature validity proves possession of the signing key, not a real-world name. The UI exposes the full public key as a comparison code before explicit acceptance. Contacts are not marked human-verified automatically.
- Acceptance re-verifies the token after acquiring the write lock, then encrypts the contact list. Self-adds, duplicate keys, and lists over 100 contacts are refused. Legacy vaults keep their identity and gain an empty contact list.
- QR codes carry the public invitation link, never a private seed or vault key. They retain a four-module white quiet zone, black modules and medium error correction in both app themes. An independent QR decoder test checks the exact resulting link.

## Threats addressed
Copying the ciphertext store without its key does not expose the profile or identity seed. Modified ciphertext/nonces fail authentication. Accidentally using the wrong key fails closed. Renaming a profile cannot change its identity. Concurrent browser sessions cannot silently replace a newer encrypted profile.

## Experimental network messaging
- RFC 9420 MLS suite 1 is implemented by pinned `ts-mls` 1.6.4. Common uses its standard MLS/HPKE/hash/KDF submodules with an explicit suite provider and Noble Ed25519 signatures, and tests interoperability with the upstream provider. The default permissive credential service is replaced with exact identity/signing-key pins.
- A public one-use key package is signed by the contact's existing Ed25519 identity. Welcome and application envelopes have transferable signatures binding sender, recipient, ID, timestamps and opaque protocol data. The MLS group is checked for exactly the intended two Common identities and leaf signing keys, the correct group ID and epoch. V2 sessions accept only identity-pinned, alternating two-member UpdatePath commits; membership changes, proposals and self echoes are rejected. Legacy v1 sessions require explicit reconnection before new sends.
- Native initialization actively checks OpenSSL-backed QuickCrypto primitives; browser initialization preserves WebCrypto and checks the same operations. Unsupported runtimes fail closed. No weaker Expo Go encryption path is provided.
- Sender state advances together with stable ciphertext and the outbox in one encrypted vault transaction before publication. Receiver state, history, sender-bound dedup record and encrypted receipt outbox persist together before acknowledgement. Lock invalidates signing capabilities, queued transactions and new transport signatures; a previously dispatched storage/network operation cannot be recalled.
- Queued, Stored and Delivered are separate states. Only a valid encrypted receipt from the accepted peer marks Delivered. Retry preserves the original ciphertext and ID; a lost HTTP acknowledgement does not re-encrypt from an old ratchet state. Expired records retain visible history with an error.
- A recipient reconnecting can process queued first-message Welcome/application packets within their expiry window. All unconfirmed outgoing packets share the claimed key-package deadline. Owner-authenticated public-key status replenishes ten available packages while retaining up to 110 matching private packages until expiry/consumption. Claimed-but-unused keys are not silently discarded to make room.
- Backpressure is isolated per recipient; missing initial packages do not prevent ready friends or incoming mail from progressing. Unknown signed senders are discarded without creating contacts. Explicit mutual Reconnect cancels old local jobs while retaining history; bounded retired groups drain stale mail that could otherwise block a new Welcome.
- The self-hostable Node service has one-use expiring signed challenges, owner-bound key publication/status, authenticated key claims, recipient-only sender+ID acknowledgements, durable atomic snapshots, TTL pruning, quotas, bounded request/response streams and restricted browser origins. Claim authentication is not recipient authorization: any different signing identity can consume public packages, and any signing identity can submit bounded mail. Recipient-issued permissions remain necessary before public hosting. It holds ciphertext and public key packages; it has no message-decryption or vault keys. TLS is required beyond literal loopback addresses.

## Limits and release gates
A compromised running app, malicious browser script/update, unlocked device, stolen vault key, or compromised OS can read data available to the active session. JS garbage collection prevents promises of immediate memory erasure. Deleting browser storage destroys the saved vault. Native SecureStore behavior after reinstall, backup/restore and device lock must be checked on hardware. Local encryption cannot prevent an attacker with write access from replaying an older valid record or deleting records; rollback protection is not implemented.

Local encryption does not itself provide messaging forward secrecy. MLS sender ratchets provide a protocol foundation, and new v2 sessions now alternate both members’ epoch updates with durable commits and authenticated acknowledgments. This is unaudited integration work, not a proven post-compromise guarantee. Stored chat history and recoverable old vault snapshots remain accessible to a holder of their vault key. `ts-mls` explicitly reports no formal security audit; internal tests/reviews are not an independent audit. Noble's public audit material does not audit Common or every installed version. Independent integration review, remaining dependency-advisory remediation, native hardware/performance testing and secure release delivery are required before production.

Invitation metadata is public to anyone who sees the link; query parameters may appear in browser history and hosting access logs. Expiry relies on the device clock. Invitations are reusable until expiry; creating a replacement does not revoke an old one. Contact acceptance is local and does not prove mutual consent or create a network session. The custom native scheme is not a verified universal/app link and may conflict with another installed app. Production web origin, link policy, native scheme behavior, camera scanning, and browser/native vault integration need review and testing before release.

The mailbox observes sender/recipient identities, key-package claims, timing, sizes and network addresses. It can withhold/delete/reorder/replay packets or cause denial of service; signatures/encryption do not guarantee availability. Any identity can currently address or claim packages for a known recipient. Public deployment needs recipient-issued capabilities, stronger abuse controls, TLS operations and monitoring. Direct peer transport, multiple/default hosted mailboxes, background/push delivery and automated simultaneous-session negotiation remain unimplemented. A closed browser receives only when reopened/unlocked. Reconnection requires both people to reset explicitly and have one send first. Web origins share storage/identity; different tabs on one origin are not separate people. Native persistence size limits and certificate behavior still need device QA.

## Nearby Wi-Fi and BLE boundary

The nearby service checks accepted contact identity on each signed challenge/request and pinned signed response. Responses bind the exact request ID and hash, including the action payload. One-use challenge, size/rate/concurrency bounds, durable claim/inbox commits and dedup tombstones prevent replay from silently duplicating accepted data. Route-specific key packages prevent independent mailbox/nearby claims of the same one-use material. MLS session/history/outbox/receipts remain shared across routes.

The signed ten-minute nearby offer binds both identities, endpoint/TLS certificate fingerprint or BLE service and time bounds. It can expose temporary hotspot credentials to the intended recipient or anyone who obtains the code. It includes no identity seed, private MLS material or TLS private key. Wi-Fi pins the exact per-session certificate only for that socket; it does not weaken global HTTPS certificate checks. BLE carries signed/MLS-encrypted application packets, but exposes routing keys, sizes and timing. Radio availability and denial of service remain outside message confidentiality guarantees.

Stop, Lock, route changes, backgrounding and stale-start generation guards cancel protocol work and native resource use; already transmitted packets cannot be recalled. Nearby only blocks LinkUp mailbox traffic and HTTP fallback, not all device or VPN network traffic. Native platform TLS/keystore operations, actual permission behavior, hotspot interface discovery, Bluetooth MTU/backpressure and physical-phone/VPN interoperability still require testing. Release 0.2.5 has since passed native assembly, 18 JVM checks and an emulator upgrade installation; these do not validate physical radios or hardware-backed key access. See `../READINESS.md` for current build evidence.

## Integrated private network

Android private-network mode uses independent WireGuard keys encrypted in no-backup storage with Android Keystore. The explicit system consent and foreground service stop on screen-off, task removal, app-lock or enrollment expiry. Native route leases bind TLS sockets/listeners to the configured overlay address and generation, and close them when consent or the tunnel is lost. Only enrolled peer /32 addresses and the LinkUp TLS port are accepted. Nearby-only delivery remains selected after loss; users must explicitly choose another mode before internet-mailbox use.

The self-hosted hub terminates WireGuard and can observe inner addresses, timing, sizes and friend-pair routing. Application TLS and MLS continue between phones. The hub policy permits only administrator-approved pairs and expires the entire enrolled interface with a startup guard and persistent timer. Hub enrollment and route lists are public configuration, not message keys. Calls are blocked in this mode pending strict overlay media handling. Ordinary update traffic and hub DNS resolution are outside the friend tunnel. Android supports one active VPN per profile; this is not a universal kill switch or anonymity guarantee.

The relay separately stores signed recipient permission lists with monotonic revisions. Missing permissions fail closed; revocation atomically tombstones queued mail and suppresses pending push hints. Restoring an older vault may produce a stale-revision error and must not silently restore revoked permissions. Legacy snapshots grant no inferred permissions. Accepted peers remain capable of nuisance traffic within quotas, and distributed global abuse still requires server operations controls.
